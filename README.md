# Go Idempotency Demo

Небольшой запускаемый пример на Go, демонстрирующий, зачем нужна идемпотентность при повторных запросах `POST /orders`, если клиент не получил ответ на первый запрос.

## Что демонстрирует проект

- Заголовок запроса `Idempotency-Key`.
- Возврат первоначального ответа при повторном запросе с тем же ключом и содержимым.
- Ответ `409 Conflict`, если повторно использовать ключ с другим содержимым запроса.
- Координацию параллельных запросов с одинаковым ключом с помощью хранилища в памяти.
- Структурированное логирование HTTP-запросов с помощью `log/slog`.
- Модульные тесты, включая проверку параллельных запросов.

## Запуск

Выполни:

```bash
go test ./...
go run ./cmd/server
```

Сервер будет доступен по адресу `http://localhost:8080`.

## Проверка работы

Первый запрос:

```bash
curl -i -X POST http://localhost:8080/orders \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: checkout-123' \
  -d '{"product_id":42,"quantity":1}'
```

Отправь точно такой же запрос повторно. В ответе должен вернуться тот же `order_id` и заголовок:

```text
Idempotency-Replayed: true
```

Теперь используй тот же ключ, но измени содержимое запроса:

```bash
curl -i -X POST http://localhost:8080/orders \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: checkout-123' \
  -d '{"product_id":42,"quantity":2}'
```

Сервер вернёт `409 Conflict`.

## Ограничения примера

Это учебный пример для одного процесса. Данные хранятся в оперативной памяти, срок хранения ключей не ограничен, а после перезапуска сервера все записи теряются. При работе нескольких экземпляров приложения общее состояние не поддерживается.

Для production необходимо хранить состояние идемпотентности в общей базе данных или Redis, определить срок хранения ключей и политику восстановления после ошибок, а также согласовать сохранение ключа с созданием заказа в рамках транзакции. Дополнительно важно предусмотреть уникальное ограничение на уровне базы данных.

Если используются внешние платёжные сервисы, необходимо также учитывать их механизмы идемпотентности и сценарии восстановления после сбоев.

**Этот проект демонстрирует основной принцип идемпотентности, но не является готовой production-реализацией.**
